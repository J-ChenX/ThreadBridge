# 开发与发布

## 文件与运行入口

源码、配置示例、测试和当前文档进入 Git；SDK、数据库、私有配置、签名、日志、截图和构建产物留在忽略的 `local/`、`artifacts/`、`target/` 或 Android build 目录。`Cargo.lock`、Gradle Wrapper JAR 和 Room schemas 是可复现构建及迁移所需输入，必须保留。Gradle distribution 校验值写入 Wrapper 配置，更新版本时与官方校验值一并更新。

生产逻辑和模块单元测试集中于 Rust。旧通知配置与 systemd 引用的 `scripts/capture_catalog.py`、`scripts/fleet.py` 只作为转交原生 CLI 的迁移启动器，不承载采集、RPC 或队列逻辑。新部署直接使用二进制子命令；远端 helper 必须换成匹配平台的二进制，不能把旧 Python helper 路径原样传给原生 RPC。更改服务配置前保存定义和数据库快照；目录整理不移动签名或运行库。

当前文档分别负责产品约束、架构、模块合同和操作方法。旧候选方案、部署过程和截图不作为源码发布内容，不把过期记录追加为当前事实。行为变更同步更新所属模块；路径变更修复调用和链接。

## 检查

```sh
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo build --release --locked
python3 tests/run.py --integration-only
```

生产采集和运维不需要 Python 解释器。Python 黑盒集成、旧路径启动器和 Android 工具保持 3.10+ 兼容，开发和 CI 使用 3.14，仅用标准库。测试直接调用真实 Rust CLI，mock 使用所选解释器。runner 从仓库根运行，`--unit-only` 执行 Rust 单元回归，`--integration-only` 执行独立 HTTP/子进程回归；用 `--binary PATH` 指定已构建 CLI。Windows job 验证原生模块单元回归和 Clippy，不运行 Linux systemd 或真实远端操作。测试详细范围见 [tests/README.md](../tests/README.md)。

Android 使用 JDK 17 和 SDK 35：

```sh
export JAVA_HOME=/path/to/jdk17
export ANDROID_HOME=/path/to/android-sdk
export PATH="$JAVA_HOME/bin:$PATH"
android/gradlew -p android :app:testDebugUnitTest --no-daemon --no-parallel
android/gradlew -p android :app:assembleDebug :app:lintDebug --no-daemon --no-parallel
```

JVM 与构建顺序执行，避免 debug/release KSP 同时写 Room schema。release 构建见 [运行与安装](运行与安装.md)。CI 验证 Rust、Python 隔离回归与无私有签名的 Android debug。Android job 显式安装 command-line tools 并设置 PATH，再准备 SDK 35/build-tools 35.0.0；不依赖 runner 预装的 sdkmanager，不操作实际部署。

涉及数据库或启动兼容时，运行 `python3 tests/integration/test_android_migrations.py` 检查所有历史 schema 与版本不回退；正式交付前还需用实际签名包在专用模拟器运行 `tests/android/qa_android_startup_upgrade.py` 的覆盖安装、启动和重启回归。已有配对场景使用 `--require-paired`，先连接隔离合成 Hub。不能用全新安装成功或源码 schema 测试替代真实上一版 APK 的升级验证，不能清除数据或卸载应用来使升级测试通过。

## Android 版本与交付门禁

根目录 `AGENTS.md` 对所有后续开发生效。修改手机用户可见功能或用户要求安装包时，完成条件包含正式版本 APK；debug 仅供内部回归，不能自行缩减为预览交付。仅文档、版本/发布流程及其测试改动可不发布产品安装包，但须说明范围。

`android/release.properties` 是唯一版本源，分别记录候选与最近已交付版本、versionCode、固定包名、上一版 APK SHA-256 和原签名指纹。Gradle、构建和验收工具共同读取它。文档不单独维护随发布变化的当前版本常量；历史文档中的 `0.1.x` 是当时的记录，不是版本选择依据。普通兼容更新默认递增修订号，主/次版本调整说明理由；三段稳定版本及 versionCode 均须高于已交付版。

正式入口为 `scripts/build-apk.sh PREVIOUS.apk`。脚本强制核对登记的上一版真实文件，串行运行 JVM、release 构建和 release Lint，再执行正式验收。禁止跳过检查、重签名替代原密钥、把 debug 改名后交付，或覆盖同版本旧产物。校验器拒绝 debug 包名、debuggable、签名变化、内部版本不匹配、文件名不匹配、版本不递增、错误的上一版文件及对齐/签名失败；它不允许省略上一版。

候选文件先进入唯一临时目录；通过全部校验后才生成 `artifacts/ThreadBridge-<version>.apk`、`.apk.sha256` 与 `.verification.json`。交付报告必须包含 `delivery_approved: true`、APK 哈希、上一版哈希及升级身份检查结果。最终答复列出版本、文件链接及实际检查范围；构建、交付、上线、真机安装分别陈述，不以其中之一冒充其他操作。缺少签名材料或上一版文件时说明具体阻塞，保留验证成果，不退回调试包。

构建不会自动将候选登记为已发布。实际交付确认后，将真实交付 APK 的版本、versionCode 和哈希登记为 published，同时递增下一个候选版本。原签名指纹保持一致；未完成交付不能修改 published 字段。GitHub 上传或生产部署仍按用户授权范围执行。

```sh
python3 scripts/release_policy.py
python3 tests/test_release_policy.py
# 构建 debug 后验证它实际读取了共同版本源；输出 delivery_approved=false。
python3 scripts/release_policy.py --check-debug-apk android/app/build/outputs/apk/debug/app-debug.apk --sdk "$ANDROID_HOME"
```

CI 的 release-policy job 要求根目录 AGENTS.md 存在且非空，并检查版本源及失败场景，Android job 检查实际 debug APK 元数据。规则回归不使用私有密钥；模拟 SDK 仅用于独立测试，不能作为正式 APK 的签名证明。正式验收始终调用真实 SDK 工具。

## GitHub 提交与分发

仓库默认分支为 `main`。新仓库先进行一次本地源码提交；提交前核对 `git status --short`、`git diff --cached --stat` 和待提交文件。`.gitignore` 不会移除已经跟踪的文件，后续意外提交的秘密需从历史清理并撤销相应凭证。

连接已创建的目标仓库后：

```sh
git remote add origin https://github.com/OWNER/ThreadBridge.git
git push -u origin main
```

把 OWNER 替换为实际仓库所有者。远端已存在时先检查 `git remote -v`，不要覆盖错误地址或强制推送。不要使用 `git add -f local/`、`git add -f artifacts/` 或提交签名材料。

APK 在检查签名和版本后通过 GitHub Releases 上传 APK 与 SHA-256；运行库、截图和服务配置不随安装包上传。选择仓库可见性和软件许可证属于项目所有者的发布决策，代码整理不会自动添加许可声明。

公开安装包构建不要继承个人 `THREADBRIDGE_PUBLIC_TEST_*` 地址；默认留空，由用户配对自己的 Hub。覆盖升级保留原签名，不能为方便公开构建替换既有私有签名。

### 自动发布 APK

`.github/workflows/release.yml` 在推送稳定三段版本标签时自动构建并发布，也可在 Actions → Release APK → Run workflow 输入已有标签补发。标签必须为 `v` 加 `android/release.properties` 中的候选 `versionName`；历史测试标签不用于当前发布流程。

首次在仓库 Settings → Secrets and variables → Actions 配置三个 Secrets：`THREADBRIDGE_KEYSTORE_BASE64`（原 keystore 的 Base64）、`THREADBRIDGE_KEY_PASSWORD`（原密码）、`THREADBRIDGE_SIGNER_SHA256`（原 APK 签名证书的 SHA-256，须与版本源一致）。签名材料不进入源码、日志或 Release 附件。

先按版本源维护候选与真实已交付基线，提交并推送源码，再创建和推送对应标签：

```sh
candidate_version=$(python3 scripts/release_policy.py --field versionName)
git tag "v${candidate_version}"
git push origin "v${candidate_version}"
```

工作流只从 `v<publishedVersionName>` 对应的 GitHub Release 下载 `ThreadBridge-<publishedVersionName>.apk`，并核对真实哈希、签名、包名和版本；不能选择“最近公开版”替代登记基线。若已交付版尚未公开，须先核实该版真实产物的公开分发安排；缺失时工作流明确失败，不降级校验，也不回退版本源。源码推送本身不要求发布 APK。

工作流调用 `scripts/build-apk.sh PREVIOUS.apk`，串行运行 JVM 测试、Release 构建和 Lint，完成原签名、16 KiB 对齐、递增版本及报告检查后，上传 APK、SHA-256 与 `.verification.json`。公开构建显式清空个人服务器预置，已存在的 Release 不覆盖。构建不会自动前移已交付登记；实际交付后按版本规则登记下一候选。

### 仓库协作与保护

首页 README 面向安装者提供功能、下载、配置和限制；公开版本记录维护在 `CHANGELOG.md`。源码采用 MIT 许可证。贡献、行为准则、支持和安全报告分别见根目录的 `CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SUPPORT.md` 和 `SECURITY.md`；Issue 和 Pull Request 使用 `.github/` 中的模板。

`main` 分支配置 `rust-python`、`rust-windows`、`android` 三项 CI 检查，合并前需解决评审讨论，禁止普通参与者强制推送或删除分支；保留仓库管理员的维护例外，不额外要求另一名评审者。合并后自动删除来源分支。GitHub Actions 的普通 CI 针对 `main` 推送及 PR，避免 Dependabot 分支推送与 PR 重复构建；版本标签由独立 APK 发布工作流处理。

Dependabot 每周检查 Cargo、Gradle 和 GitHub Actions 依赖，并以 PR 提议更新；不自动合并。启用依赖漏洞提醒、安全修复 PR、秘密扫描及推送保护，以及私密漏洞报告。工作流和依赖更新仍需审查兼容性、固定版本和 CI 结果。
