# 开发与发布

## 文件与运行入口

源码、配置示例、测试和当前文档进入 Git；SDK、数据库、私有配置、签名、日志、截图和构建产物留在忽略的 `local/`、`artifacts/`、`target/` 或 Android build 目录。`Cargo.lock`、Gradle Wrapper JAR 和 Room schemas 是可复现构建及迁移所需输入，必须保留。Gradle distribution 校验值写入 Wrapper 配置，更新版本时与官方校验值一并更新。

生产逻辑和模块单元测试集中于 Rust。旧通知配置与 systemd 引用的 `scripts/capture_catalog.py`、`scripts/fleet.py` 只作为转交原生 CLI 的迁移启动器，不承载采集、RPC 或队列逻辑。新部署直接使用二进制子命令；远端 helper 必须换成匹配平台的二进制，不能把旧 Python helper 路径原样传给原生 RPC。更改服务配置前保存定义和数据库快照；目录整理不移动签名或运行库。

当前文档分别负责产品约束、架构、模块合同和操作方法。旧候选方案、部署过程和截图不作为源码发布内容，不把过期记录追加为当前事实。行为变更同步更新所属模块；路径变更修复调用和链接。

## 检查

```sh
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo build --release --locked
python3 tests/run.py --integration-only
```

生产采集和运维不需要 Python 解释器。Python 黑盒集成、旧路径启动器和 Android 工具保持 3.10+ 兼容，开发和 CI 使用 3.14，仅用标准库。测试直接调用真实 Rust CLI，mock 使用所选解释器。runner 从仓库根运行，`--unit-only` 执行 Rust 单元回归，`--integration-only` 执行独立 HTTP/子进程回归；用 `--binary PATH` 指定已构建 CLI。Windows job 验证原生模块单元回归和 Clippy，不运行 Linux systemd 或真实远端操作。测试详细范围见 [tests/README.md](../tests/README.md)。

Android 使用 JDK 17 和 SDK 35：

```sh
export JAVA_HOME=/path/to/jdk17
export ANDROID_HOME=/path/to/android-sdk
export PATH="$JAVA_HOME/bin:$PATH"
android/gradlew -p android :app:testDebugUnitTest --no-daemon --no-parallel
android/gradlew -p android :app:assembleDebug :app:lintDebug --no-daemon --no-parallel
```

JVM 与构建顺序执行，避免 debug/release KSP 同时写 Room schema。release 构建见 [运行与安装](运行与安装.md)。CI 验证 Rust、Python 隔离回归与无私有签名的 Android debug。Android job 显式安装 command-line tools 并设置 PATH，再准备 SDK 35/build-tools 35.0.0；不依赖 runner 预装的 sdkmanager，不操作实际部署。

## GitHub 提交与分发

仓库默认分支为 `main`。新仓库先进行一次本地源码提交；提交前核对 `git status --short`、`git diff --cached --stat` 和待提交文件。`.gitignore` 不会移除已经跟踪的文件，后续意外提交的秘密需从历史清理并撤销相应凭证。

连接已创建的目标仓库后：

```sh
git remote add origin https://github.com/OWNER/ThreadBridge.git
git push -u origin main
```

把 OWNER 替换为实际仓库所有者。远端已存在时先检查 `git remote -v`，不要覆盖错误地址或强制推送。不要使用 `git add -f local/`、`git add -f artifacts/` 或提交签名材料。

APK 在检查签名和版本后通过 GitHub Releases 上传 APK 与 SHA-256；运行库、截图和服务配置不随安装包上传。选择仓库可见性和软件许可证属于项目所有者的发布决策，代码整理不会自动添加许可声明。

公开安装包构建不要继承个人 `THREADBRIDGE_PUBLIC_TEST_*` 地址；默认留空，由用户配对自己的 Hub。覆盖升级保留原签名，不能为方便公开构建替换既有私有签名。

### 自动发布 APK

`.github/workflows/release.yml` 在推送 `v` 开头的版本标签时自动构建并发布，也可在 Actions → Release APK → Run workflow 输入已有标签补发。标签必须对应 APK 的完整 `versionName`，例如当前版本为 `v0.1.21-test`；带后缀的版本发布为 Pre-release。

首次在仓库 Settings → Secrets and variables → Actions 配置三个 Secrets：`THREADBRIDGE_KEYSTORE_BASE64`（原 keystore 的 Base64）、`THREADBRIDGE_KEY_PASSWORD`（原密码）、`THREADBRIDGE_SIGNER_SHA256`（原 APK 签名证书的 SHA-256）。签名材料不进入源码、日志或 Release 附件。

每次发布先修改 `android/app/build.gradle.kts` 的 `versionName` 并递增 `versionCode`，提交、推送源码，再创建并推送对应标签：

```sh
git tag v0.1.21-test
git push origin v0.1.21-test
```

工作流串行运行 JVM 测试、Release 构建和 Lint，验证标签与 APK 版本一致、原签名、对齐、SHA-256，并与上一份公开 APK 比较包名、签名和版本递增后上传。公开构建显式清空个人服务器预置。已存在的 Release 不覆盖；历史版本不要求逐个补齐，优先发布最新可用版本。
