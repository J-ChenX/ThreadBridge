# 滚动与图片性能评估（0.1.19）

## 虚拟滚动

主页、侧边栏、收藏列表和对话页已经使用 Compose `LazyColumn`，按可见条目创建、布局并复用内容。无需再引入一个虚拟滚动库。主页“展开全部”继续使用有稳定 ID 的惰性条目，项目固定栏也保留。[Android 官方列表说明](https://developer.android.com/develop/ui/compose/lists)

对话页的虚拟化单位是连续同角色的消息组：该组内正文和已展开过程仍使用 `Column`。这意味着一条很长的助手回复、或大量连续过程说明，并不会逐段虚拟化。数据库读取有初始 100 条、逐步分页及 5000 条窗口上限；这些限制不能替代组内虚拟化。后续如实机出现此类滚动卡顿，应优先把消息组拆为稳定的正文/过程/时间条目，并保持向下展开锚点、文字选择和时间段显示，再考虑长正文分段。当前没有引入嵌套滚动。

## 本次落实的优化

- 同角色分组由反复复制增长列表改为可变构建后一次封装，复杂度从最坏 O(n²) 降至 O(n)；一万条连续助手消息用例检查原始顺序。分组结果按消息/待发送内容缓存，输入草稿不重复构建整段消息组。
- 设备归属一次分桶，避免每个设备都扫描所有对话；每个设备的项目排序同时供固定栏和正文复用。同步删除对照使用 ID 集合，避免逐条扫描完整远端列表。
- 为项目、对话和角色消息条目标记内容类型，改善同类型布局复用；保留原有稳定 ID。
- 图片缩略图最长边按 720 解码，打开查看器后才按 1600 加载；解码和文件操作在 IO 调度器执行。2400×1600 样图的缩略图采样从 1200×800 改为 600×400；按 ARGB 四字节估算，单张像素内存从约 3.84 MB 降到 0.96 MB。这是像素内存计算，不是整机内存实测。[Android 官方采样说明](https://developer.android.com/topic/performance/graphics/load-bitmap)
- 增加按连接/集合、对话、内容摘要及解码尺寸隔离的 8 MiB Bitmap LRU。滚出再进入复用解码结果，图片原始文件缓存仍限制 64 MiB；删除、七天清理和集合/配对重置清除对应内存。缩略图加载前后占位一致，避免图片加载推动正文。

## 仍需测量的边界

同步仍串行保障凭证/集合和缓存一致性；网络较慢时图片首次请求会等待同步门，当前没有绕过该保护。全量标题索引同步、超长单组排版和大量正文的文字测量是后续重点，宜在真实手机的 Release 包上用 Perfetto/帧时间和内存采样确定优先级。此次模拟器验证只证明行为与边界正确，没有得出真机 FPS、耗电或百分比提速结论。

七天清理策略保持原样；十分钟前的对话读完后退出默认预览，是预览条件变化。每个项目提供“展开全部”，并用实际 Room 检查确保此时记录没有被删除。
