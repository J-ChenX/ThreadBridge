# 多机接入与统一启停

## 配置与职责

Rust CLI 支持一个 Hub 电脑与最多三个远端，每台具有独立身份、捕获库、版本配置与队列账本。远端原生二进制的 `remote-capture` 通过已信任 SSH/Tailscale 接收固定 JSON RPC，操作白名单、响应大小和时间有界。Linux 使用 shell 参数引用，Windows 使用固定 PowerShell 命令和 UTF-8 管道；不向远端发送 Python 或任意业务代码。

私有清单位于 `local/fleet/fleet.json`，模板为 `deploy/fleet.example.json`。填写本机 binary、hub_db、host_id、SSH、helper、Codex 和 CODEX_HOME。helper 必须是远端 `threadbridge`/`threadbridge.exe`，不能继续填写 `remote_capture.py`；旧 python 字段不再使用，可删除。remote_binary 指向本机准备上传的匹配平台构建产物，Windows 必须明确提供 PE，Linux 必须是 ELF。

verified_version 默认 null，即只读；验证原 ID、上下文和权限后才设置精确版本。SSH 使用 BatchMode、StrictHostKeyChecking 和超时，先配置密钥与 known_hosts，不绕过主机指纹。

```sh
mkdir -p local/fleet
cp deploy/fleet.example.json local/fleet/fleet.json
# 编辑路径和身份，再检查已有连接
target/release/threadbridge fleet --config local/fleet/fleet.json probe
```

## 原生部署与旧配置迁移

先保存服务定义、私有清单及 SQLite 一致性快照，为每个目标准备匹配平台的二进制。将旧 helper .py 路径改为新程序路径，设置 remote_binary。程序与 remote.json 同目录，捕获数据仍使用 data/replies.sqlite、原 collection 文件、health 双槽和队列账本。

```sh
target/release/threadbridge fleet --config local/fleet/fleet.json deploy
target/release/threadbridge fleet --config local/fleet/fleet.json install
target/release/threadbridge fleet --config local/fleet/fleet.json start
target/release/threadbridge fleet --config local/fleet/fleet.json status
```

deploy 上传原生 helper 和配置；install 修改本机用户服务，应先检查清单与既有服务。旧 scripts/fleet.py 只启动同一 Rust CLI，可暂时保留旧 systemd 的本机路径；原生 RPC 仍要求远端已迁移。新部署无需远端 Python。

## 生命周期与恢复边界

原生 JSONL 单行最多 20 MiB，包括同一条消息中全部图片的 base64 内容、文本和元数据；会话元数据行仍限 4 MiB。图片采集、Hub 导入及 Android 解码字节上限统一为 20 MiB（原生记录还受 base64 后整行 20 MiB 限制）；Android 图片 JSON 响应上限为 28 MiB，以容纳 base64 开销。每条消息最多 16 张图片、用户文本仍限 256 KiB，扫描总量和数据库预算保持有界。先前失败的轮询按已确认轮次重试，补入缺失消息。

start/stop/restart 控制 threadbridge.target，包含既有 threadbridge-phone-hub、threadbridge-phone-inbox、threadbridge-phone-capture 和 remote 实例。install 不创建三个本机基础服务，先按[运行与安装](运行与安装.md)配置。生成的 remote 服务直接运行原生 fleet 子命令。

远端只读取确定的 completed/final 和当前轮次人类输入，将独立 SQLite 快照幂等导入 Hub。身份由 host/native ID 决定，不按标题路由。发送仅调用精确版本验证后的 queue；失联停止刷新就绪状态，历史仍可读。重连只核对原请求，不重投 unknown。

.collection.json 的 cutoff、完整旧 ID 排除集和 generation 约束所有入口；跨进程锁协调采集与删除。删除只影响 ThreadBridge 副本，保留原 Codex、配对与必要账本。resume 在发布租约和保存 final 前也核对策略，被排除或禁用后停止并保留未知回执。

`threadbridge capture-health --database PATH` 读取持久状态。离线恢复先停止 fleet poller，运行 `recover-capture-health --config REMOTE_JSON --database PATH prepare` 创建备份，再执行 `batch DIRECTORY`，覆盖全部目标后 `finalize DIRECTORY`。CODEX_HOME 必须对应原索引。恢复保留原失败，不修改正文库、不发送消息；绑定、索引或源文件变化时拒绝 finalize。

四机重置使用 `collection-reset --config ...` 先只读规划，只有 --apply 才停止 target、安装禁用策略、清除副本、最终重建 baseline 并恢复服务。原 Codex 与设备凭证不变；中途失败保持 target 停止。它会影响手机缓存，不能当作普通状态检查。

## 备份、回退与验收

fleet install 在本机 local/backups/fleet-* 保存原定义。回退先停止 target，恢复具体服务片段，保留其他 drop-in，执行 systemctl --user daemon-reload，恢复同版本本机/远端程序与私有清单后启动。不能用旧正文库覆盖最新 collection 或未知发送账本。旧 Python 运行链路源码恢复基线为 Git c39a2c5。

Rust 单元回归覆盖固定 RPC、快照、扫描水位、健康恢复、平台命令与丢失确认不重投；`tests/run.py --integration-only` 验证真实 CLI、回环 HTTP、重启和身份隔离。测试不登录真实电脑。各系统实机验收仍需验证原 ID/上下文、停止后就绪撤销、重连、未知回执、开机恢复和持续资源曲线；隔离回归不等于四机迁移已部署。

手机对话列表按发起对话的桌面电脑分组，执行与在线状态仍使用原机器。远端采集器读取 Codex 桌面的显式 SSH 项目归属（`thread-project-assignments` 与 `thread-project-membership-host-ids` 必须一致），Hub 单独保存显示归属并提供 `display_host_id`；`host_id`、原生对话 ID 和续聊路由保持不变。Android 缓存增加显示归属列，以保留升级前的草稿和配对。未知或冲突归属回退到执行机器，读不到桌面状态时保留已确认归属。

在发起端的 fleet 主机配置中增加 `desktop_remote_hosts`，将 Codex SSH 主机标识映射为已有 fleet 名称，例如 Windows 的 `{"remote-ssh-discovered:lerrem-server":"lerrem","remote-ssh-discovered:echova-dev":"echova"}`。已映射服务器上的新 SSH 对话会自动沿用发起电脑分组；增加 SSH 服务器时需要补充映射。项目目录和路径不用于猜测主机。

远程项目名称和对话归属读取发起端桌面的 `remote-projects`、`thread-project-assignments` 与 `thread-project-membership-host-ids`，由同一映射解析执行主机。远程服务器的本地项目表可能没有这些项目，不能据此把已有桌面归属降为“其他”。Hub 单独保存桌面元数据并优先用于对话项目展示；服务器本地采集刷新不会覆盖它。项目新建、改名、移入或移出即使没有新回复，也随每次快照轮询更新。桌面状态缺失或损坏、发起电脑离线时保留上次元数据，明确删除后才移除；跨主机不一致的归属不采用，多桌面冲突时回退本地分类。

此修复需要同时更新 Hub/fleet 二进制与发起端的采集 helper；Android 沿用已有 `project`、`project_name`、`project_known` 字段，正常同步后更新分类。它不修改原始对话、执行主机、发送授权或未读状态；桌面目录元数据本身不授予新建对话的执行权限。

升级服务端时必须保留手机使用的接口契约：配对响应与 `/v1/hosts` 返回同一个持久化 `hub_id`，任务列表继续提供 `task_status`、`task_turn_id` 和 `display_host_id`。`hub_id` 保存于 Hub 的 `settings`，只在缺失时初始化；升级、换入口和重启均不能重新生成身份或清空配对。发布验证应直接请求实际 Hub HTTP 接口，覆盖旧数据库中已有身份的保留，不能由测试代理补写缺失字段。

某两台电脑的 Tailscale 路径长期走低吞吐中继时，小包 ping 成功不能证明完整快照能在 RPC 时限内下载。可先对比原路径和已有可信主机的 SSH `ProxyJump`：目标仍使用原 Tailnet 地址及原主机指纹，SSH 连接在发起端与目标端之间加密。只对该目标设置跳板，并保留 SSH 配置备份；跳板必须在线，否则该目标无法采集。不要通过延长就绪租约或清除健康失败来掩盖传输超时。
